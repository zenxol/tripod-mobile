# Tripod Mobile

iPhone version of Tripod (pickleball instant replay). **Current state: home screen, live rear-camera preview, plain Start/Stop video recording, and a test-only Start/Stop Buffer control for the rolling replay buffer** (native Swift/AVFoundation module in `modules/tripod-camera`). There's no replay playback or Save Replay yet.

| | |
|---|---|
| Stack | Expo SDK 58, React Native 0.88, React 19.3, TypeScript |
| iOS | Bundle ID `com.zenxol.tripod`, iOS 16.4+ (SDK 58 minimum), iPhone only |
| Native code | Generated by `expo prebuild` (Continuous Native Generation): `ios/` is **not** committed and is never edited by hand |
| CI | GitHub Actions on `macos-26` (Xcode 26.6) compiles an **unsigned** build |

## Run locally on Windows

```powershell
npm install          # or: npm ci
npx expo start       # starts the JavaScript dev server and shows a QR code
npx tsc --noEmit     # typecheck
npx expo-doctor      # check dependency and config problems
```

**Previewing on your iPhone (no Mac needed, for now):** install **Expo Go** from the App Store, connect the iPhone to the same Wi-Fi as the Surface, and scan the QR code from `npx expo start` with the iPhone camera.
- This works only while the app uses no custom native code. Once a Swift module is added, a custom-built app is needed instead.
- Expo Go only supports recent Expo SDKs. If it says the project's SDK is unsupported, that's an Expo Go limitation, not a project error.

What can't be done on Windows: `npx expo prebuild --platform ios` (Expo refuses to generate the iOS project on Windows), CocoaPods and Xcode. Those run in GitHub Actions.

## Build iOS in GitHub Actions

Workflow: [`.github/workflows/ios-build.yml`](.github/workflows/ios-build.yml)
1. **Checks the Xcode version.** The build fails with a clear message if it's below 26.4.
2. **Installs dependencies:** Node 24, then `npm ci`.
3. **Generates the native project:** `npx expo prebuild --platform ios --clean --no-install`.
4. **Installs CocoaPods:** `pod install`.
5. **Compiles:** `xcodebuild` for real iPhones (`-sdk iphoneos`, Release) with **code signing disabled**.
6. **Uploads** `Tripod-unsigned.ipa` (plus a README) as the `tripod-ios-unsigned` artifact, kept for 14 days. If the build fails, it uploads `xcodebuild.log` instead.

### Trigger it
The workflow is **manual-only**. On a private repo, macOS minutes count 10× against the free monthly allowance (2,000 minutes, so about 200 macOS minutes).
1. Push this repo to GitHub (see below).
2. Open the repo on github.com, then **Actions** → **iOS build (unsigned)** → **Run workflow** → choose `main` → **Run workflow**.
3. With the GitHub CLI, if installed: `gh workflow run ios-build.yml`, then `gh run watch`.

### Download the artifact
- **Web:** open the finished run (**Actions** → click the run) and scroll to **Artifacts** → **tripod-ios-unsigned**. It downloads as a `.zip` containing `Tripod-unsigned.ipa` and `README.txt`.
- **CLI:** `gh run download --name tripod-ios-unsigned`.

### Important: what the artifact is and isn't
- A green run proves the app **compiles** for iOS devices with the generated native project.
- It does **not** prove the app installs or runs on an iPhone. iOS only installs apps signed with a certificate and provisioning profile.
- **The unsigned `.ipa` can't be installed directly.** It would have to be signed with your Apple Account first, which is a later task, with free-account limits: 7-day certificates and a limited number of apps or devices.

## Native camera module (`modules/tripod-camera`)

A local Expo module (Expo Modules API, Swift). Expo autolinking picks up every folder in `modules/`, and `expo prebuild` + `pod install` link it into the iOS project, so the CI workflow builds it without changes.

| File | Role |
|---|---|
| `expo-module.config.json` | Declares the Apple module class `TripodCameraModule` |
| `ios/TripodCamera.podspec` | CocoaPods spec (depends on `ExpoModulesCore`, links AVFoundation) |
| `ios/TripodCameraModule.swift` | JS module `TripodCamera`: permission functions, `startRecording`, `stopRecording`, event `onRecordingFinished`, and the native view (prop `active`, event `onCameraStateChange`) |
| `ios/TripodCameraView.swift` | `ExpoView` hosting an `AVCaptureVideoPreviewLayer`; attaches to the shared session while on screen and keeps the screen awake |
| `ios/CameraSessionController.swift` | The app's single camera (`CameraSessionController.shared`): one `AVCaptureSession` (rear wide camera) plus an `AVCaptureMovieFileOutput`, all on a private serial queue |
| `ios/CaptureConfiguration.swift` | Capture quality policy: camera, rotation, format/frame-rate targets and fallbacks, codec preference |
| `ios/RollingBufferRecorder.swift` | Rolling replay buffer: `AVCaptureVideoDataOutput` frames → `AVAssetWriter` 5 s segments, retention, diagnostics |
| `index.ts` | TypeScript wrapper. Uses `requireOptionalNativeModule`, so Expo Go and web show a message instead of crashing |

Camera frames go directly from the session to the preview layer and the movie file; nothing crosses the JavaScript bridge. The camera permission text is `ios.infoPlist.NSCameraUsageDescription` in `app.json`.

**Rolling replay buffer (Task 4A; `startBuffer()` / `stopBuffer()`, event `onBufferStatus`):**
- **One session, one encoder:** starting the buffer swaps the movie file output out of the session for an `AVCaptureVideoDataOutput`, and stopping swaps it back. The camera, its format and the preview are unchanged. Recording and buffering refuse to start while the other runs (`ERR_BUFFER_ACTIVE`, `ERR_RECORDING_ACTIVE`).
- **Pipeline:** camera frames arrive in the camera's native pixel format and orientation on a dedicated queue and are appended straight to an `AVAssetWriter` (HEVC, else H.264; AVFoundation's recommended settings for the output, plus 1 s keyframes). The portrait rotation is stored as a track transform; pixels are never rotated or converted. No frames are held in memory.
- **Segment rotation:** at the first frame whose timestamp is ≥ 5 s after the segment's first frame. That frame starts the next segment, and the old one ends exactly at its timestamp, so the timeline has no holes. The next writer is created and started in advance on another queue.
- **Files:** `tmp/rolling-buffer/writing_NNNNNN.mov`, renamed to `segment_NNNNNN.mov` only after `finishWriting` succeeds. Each segment records its file name, capture-clock start/end, wall-clock start/end, duration, frame count and size.
- **Retention:** after each segment, the oldest segments are deleted while the rest still cover 120 s + 10 s margin, so about 130–135 s is kept (≈ 27 segments). The folder is emptied on every Start Buffer and on launch. Stop Buffer keeps the last buffer's files until then.
- **Storage guard:** starting needs room for the whole buffer (estimated from the encoder bitrate) plus 300 MB; the buffer stops with `ERR_LOW_STORAGE` if free space falls below 300 MB.
- **Interruptions:** the open segment is finished and kept (with extra background time requested from iOS), the status becomes `paused`, and buffering resumes with a new segment (`followsGap: true`) when frames return. Closing the camera stops the buffer first, then the session.
- **Diagnostics (`onBufferStatus`, `getBufferStatus()`, `getBufferSegments()`):** state, segment count, buffered seconds, storage bytes, codec/size/fps, frames written, frames dropped by the camera or the encoder, frames missing according to timestamps, gaps, discontinuities between segments, failed segments, and the newest segment. Native logs: subsystem `com.zenxol.tripod`, category `buffer`.

**Recording (Task 3B milestone, used while the buffer is off):**
- **Format:** picked from the camera's actual formats. It tries 1080p60, then 1080p30, then 720p60, then 720p30, then the default `.high` preset. Only 8-bit SDR formats are used; it prefers non-binned formats and the widest field of view. The frame rate is locked (min = max), and drops to 30 fps while the phone reports serious thermal pressure.
- **Same settings everywhere:** the format is set on the device, so the preview and the recording match. Stabilization is off and both use the same rotation, so the recorded framing equals the preview.
- **Codec:** HEVC when the output supports it, else H.264. Portrait, video only (no audio, so no microphone permission).
- **Reporting:** the actual settings (read back from the device) arrive with the `running` camera state (`settings`), appear under LIVE, and go to the JS console. The saved file's resolution, frame rate and codec are read from the file itself. Native logs use subsystem `com.zenxol.tripod`, category `camera`.
- Written to `tmp/recording-in-progress/`, checked (readable, has video, duration > 0), then moved to `Documents/Recordings/recording_YYYYMMDD_HHMMSS_<6 hex>.mov`. Leftovers in the in-progress folder are deleted on launch.
- `stopRecording()` resolves with `{ uri, fileName, durationSeconds, width, height, frameRate, codec, sizeBytes, startedAt, endedBy, note? }`. `onRecordingFinished` fires for every ending, including interruptions, low storage (< 200 MB while recording) and Stop Camera.
- Recording refuses to start below 500 MB free. `Documents` is visible in the Files app under **On My iPhone → Tripod** (`UIFileSharingEnabled`, `LSSupportsOpeningDocumentsInPlace`).

Because of this module, **Expo Go can no longer show the camera**. The home screen still loads there, but Start Camera explains that the iOS build is required.
